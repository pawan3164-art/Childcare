# Privacy Impact Assessment (Draft)

Status: drafted Stage 5 (Hardening), based on what is actually built (Stages 0-4). **This is not a substitute for independent legal/privacy review** — Delivery Plan §9 explicitly calls for independent legal review of privacy terms before pilot, and this document should be the input to that review, not the output of it. BRD §33 names the OAIC's Australian Privacy Principles (APPs) and the Children's Online Privacy Code as the relevant frameworks.

## 1. What personal information is collected, and why

| Category | Examples in this system | Collected from | Purpose |
|---|---|---|---|
| Child personal information | Name, date of birth, room assignment | Centre staff at enrolment (not yet built — see OI-10) | Core service delivery: attendance, care records, billing |
| Child health information (sensitive) | Medication authorizations/administrations, incident records | Guardians (authorization), educators (administration/incident records) | Child safety, BRD §14 |
| Family/guardian personal information | Name, email, relationship type, pickup authorization | Guardians, centre staff | Account access, communication, pickup verification |
| Financial information | Fee schedules, invoices, ledger entries, payment references | Generated by the system; payment method details go to the (currently mocked) payment gateway, never stored here | Billing, BRD §15 |
| Government-related information | CCS enrolment reference, subsidy entitlement/confirmation | Guardians (enrolment), Services Australia (currently mocked — Stage 4) | CCS subsidy processing |
| Operational/audit information | Audit log entries, sync operation records, session records | Generated by the system | Security, compliance, dispute resolution |

**Children's data is the highest-sensitivity category here.** The Children's Online Privacy Code (if and when it applies — BRD flags this as "as applicable," not yet confirmed) and APP 3/6 (collection and use limits) apply directly.

## 2. Data flows and where data lives

- **Residency**: all tables are hosted in a single PostgreSQL instance, intended for AWS ap-southeast-2 (Sydney) per BRD §18 — not yet deployed to AWS at all (currently local dev only). No production data exists anywhere yet.
- **Third parties currently in the data path**: none for real — the payment gateway (`PaymentsService`) and CCS gateway (`CcsService` / `MockCcsGateway`) are both mocked. When real integrations are built (OI-12, OI-14), each needs its own APP 8 cross-border assessment if the provider processes data outside Australia.
- **Media (photos/videos)**: BRD §17 requires private storage with short-lived signed URLs; Stage 1 built the *permission logic* (which guardian can see which asset) but not real file storage (OI-09) — no actual photo/video bytes are handled by the system yet, so there is currently no media-specific privacy exposure, but this is a gap to close before any real photo is uploaded, not after.

## 3. Access controls (APP 11 — security of personal information)

- **Tenant isolation**: PostgreSQL row-level security enforces the organisation boundary at the database level, independent of application code correctness (ADR 0001). Verified in `test/access-control/tenant-isolation.spec.ts`, including that a query with no tenant context set returns zero rows rather than erroring or leaking data.
- **Relationship-based access**: a guardian can only see a specific child's data if a `GuardianChildRelationship` exists and is not restricted/expired (`AuthorizationService`). Covered for every persona (parent, educator, centre admin, org admin) in `test/access-control/authorization.spec.ts`.
- **Multi-child media visibility**: a photo tagging multiple children is visible to a guardian only if every tagged child's permissions allow it (BRD §17), tested in `test/care-loop/media-visibility.spec.ts`.
- **MFA**: available for privileged/staff accounts (TOTP via `otplib`), not yet mandatory-enforced at the application layer (no check blocking login without MFA for admin roles) — a gap worth closing before pilot.
- **Session revocation**: fixed in Stage 5 — logout/revocation now actually invalidates a JWT before its natural expiry (previously a no-op, see the Stage 5 security review).

## 4. Data minimisation and retention (APP 3, APP 11.2)

- **Not yet implemented**: no data retention/deletion policy or automated purge job exists. BRD §18 requires "data retention and deletion policies" — this is an open item, not yet built in any stage.
- **Logging hygiene**: the structured logging standard (`/CLAUDE.md`) explicitly prohibits logging child PII, payment data, or message/photo content — logs carry identifiers (`childId`, `centreId`), not personal content. Verified by code review in the Stage 5 security pass (no service logs full request/response bodies; `pino-http` redacts `req.body`/`res.body`/auth headers globally).
- **AI/ML**: no AI features are built yet (Phase 3 scope per BRD §11/§24) — the BRD's requirement that child data never trains external models without explicit lawful authority is not yet a live risk, but should be designed in from the start of Phase 3, not retrofitted.

## 5. Individual rights (APP 12, APP 13 — access and correction)

- **Not yet implemented**: no self-service "export my data" or "correct my data" flow exists for parents. Given BRD §18 requires "data export/access mechanisms where required," this is an open item for a future stage, not covered by Stages 0-4.
- Guardians can view their own child's data through the built read endpoints (Child-at-a-Glance, attendance/care-record history, ledger breakdown) — this is partial coverage of "access," not a formal APP 12 request-handling process.

## 6. Children's Online Privacy Code considerations

Not yet assessed against the actual Code text (BRD treats this as "as applicable" and unresolved). Flagging specific features that would need scrutiny once the Code's applicability is confirmed:
- Default settings for notification preferences and media visibility (the Code generally expects privacy-protective defaults for children).
- No current feature allows a child themselves to interact with the system (all interactions are staff/guardian-initiated), which likely simplifies applicability but should be confirmed, not assumed.

## 7. Recommendations before pilot

1. Independent legal review of this document and the actual data flows (Delivery Plan §9 requirement).
2. Confirm Children's Online Privacy Code applicability with the OAIC or legal counsel (BRD §33).
3. Close the retention/deletion policy gap (nothing built yet).
4. Decide whether MFA should be *enforced*, not just available, for admin/staff roles before pilot.
5. Re-run this assessment once real media storage (OI-09), a real payment gateway (OI-12), and real CCS integration (OI-14) are built — each changes the data flow picture materially.
